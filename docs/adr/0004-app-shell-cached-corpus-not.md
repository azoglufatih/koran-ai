# The service worker caches the App Shell, not the corpus

`public/sw.js` caches the app's own HTML, JavaScript, CSS and icons, and lets every request for the corpus — the vendored translations, the tafsir, and the Retrieval Index under `/content/` — go to the network untouched. That is a deliberate line, not an unfinished one: offline reading was scoped out of the MVP (#1) and installability scoped in, and installability is what the service worker is here for. Caching the corpus is the obvious-looking next step for anyone reading this code, so: it is a feature with its own decisions to make — which of 114 Surahs in which of three languages, when they are evicted, what a reader is shown when only some of it is there — and none of those have been made.

The Arabic is the exception the line cannot cover. It is bundled rather than fetched (`src/content/bundled-quran.ts`), so it reaches the reader inside the prerendered pages and the JavaScript chunks — as part of the App Shell, under a hashed name, indistinguishable from the app it is compiled into. Caching the shell caches it. The effect is that a reader who has opened a Surah can open it again with no network and see the Arabic; a translation, a tafsir or a question still needs one. That is a by-product of where the text already lives, not the offline reading the MVP deferred, which is about having the corpus deliberately — any Surah, in the reader's language, whether or not they have been there before.

The AI Client's calls are covered by the same rule from the other side: the worker answers nothing that is not a `GET` within its own scope, so a question put to a reader's provider, and the key it carries, reach the network exactly as if no worker were installed (ADR 0001).

The shell is cached as the reader loads it rather than precached at install, because the build output is named by content hashes that a hand-written worker cannot know ahead of time. Those hashed files are served cache-first — the name changes when the contents do, so a hit cannot be stale. Everything else of the app's own is served from the cache while a fresh copy is fetched behind it, which means a deploy reaches an already-installed reader one visit late. Trade-off accepted: the alternative is making every repeat visit wait on the network for a shell that has almost always not changed.

Because the reader's own browser is where all of this is kept, it stays inside the same trust boundary as their bookmarks and their provider config: a cache in their browser, cleared with the rest of the site's data, sent nowhere.
